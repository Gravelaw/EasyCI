1What DevOps is

Writing code is half of shipping software. The other half happens around the code: checking that a change didn't break anything, building what users install, recording what was released, and being able to roll back.

DevOps is the name for that second half and for the habit of automating it. "Dev" is development (writing code); "Ops" is operations (building, releasing, running it). The idea is that repetitive steps are done by machines, the same way every time, rather than from memory.

In a kitchen, cooking is development. DevOps is the routine around it: tasting before a plate goes out, labelling and dating what goes in the fridge, writing down which recipe version you used so the next batch tastes the same.

2What CI/CD is, and why JuliaFlow needs it

CI, Continuous Integration: every time the code changes, a machine runs the full set of checks and answers pass or fail, within minutes or hours, while you still remember what you changed.

CD, Continuous Delivery: when a version passes and you want to release it, a machine builds the release package the same way every time, records exactly what went in, and stores it safely.

One JuliaFlow change can touch three different worlds at once. These are the checks in its .github/workflows/ci.yml:

CheckWhat it does
webInstalls packages, validates the data contracts, builds the web app, runs unit tests, checks documentation and requirement traceability.
juliaInstalls the exact Julia packages and runs the Julia test suite, including the 100 Gateway Repository and 221 Worker Service tests, against a real PostgreSQL database.
release gateBuilds the whole product, starts it, and drives five real browser tests with Playwright against the live back end. Allowed up to 180 minutes.

Nobody can do all of that by hand after every edit. Without CI, a change to a web form could quietly break a Julia endpoint and you'd find out weeks later. With CI, the pull request shows a red cross the same day, with the log of the step that failed.

For AI coding agents this matters even more. Agents make many changes quickly, and CI is the referee that checks whether a change is actually good instead of trusting the agent's own report.

3What GitHub Actions does, and why it costs money

GitHub Actions is GitHub's built-in CI/CD service. The files in .github/workflows/ tell it: "when a pull request opens, start a fresh Linux computer, fetch the code, install Node and Julia, run these commands." GitHub rents you that computer (a runner) for the length of the job, then throws it away. The ticks and crosses on a pull request come from these runs.

It costs money because GitHub is lending you real computers. For private repositories, which JuliaFlow and EasyCI both are, you get a monthly allowance (about 2,000 minutes on the free plan, 3,000 on Pro) and then pay per minute. Since January 2026 a standard Linux runner costs about $0.006 a minute; Windows about $0.010; macOS about $0.062. Public repositories are free.

One week of JuliaFlow pushes, roughly

web ≈ 15 min julia ≈ 30–60 min release gate ≈ 60–180 min

One push uses about 2–4 runner-hours. Ten pushes a week uses up a 2,000-minute allowance in roughly a week.

After that the cost is a few dollars a week. But if the spending limit is $0, GitHub simply stops starting jobs. That is what happened on a JuliaFlow pull request: the jobs never began, so there was no answer at all.

GitHub also lets you connect your own computer as a "self-hosted runner", and those minutes are currently free. GitHub announced a small fee for them in December 2025 and withdrew it after complaints, so that could change again.

4How the local approach differs

The local approach runs the same checks on your own PC. Here that means a dedicated Linux environment inside Windows (WSL, the juliaflow-ci-ubuntu24 distro) with the right versions of Node, Julia and PostgreSQL installed once.

JuliaFlow already tried a do-it-yourself version (its scripts/ci/ runner). It works, and it taught three lessons that EasyCI is built around:

  1. Runs must not die when a window closes. Several JuliaFlow runs stopped when the terminal or agent session that started them ended, and were left saying "running" forever. EasyCI starts each run as its own background process.
  2. Stuck runs must be noticed. One Julia package install sat silent for over seven minutes until a person stopped it. EasyCI watches for silence and marks a run as stalled.
  3. Results must show up where you look. Local passes were invisible on GitHub, where the pull request just said "skipped". EasyCI posts the result back to the pull request using your existing GitHub login.

5What Jenkins is and does

Jenkins is the oldest and most widely used CI server you run yourself. It gives you a web dashboard, a job queue, a list of worker machines ("agents"), and over a thousand plugins. A Jenkinsfile lists a job's steps.

The earlier EasyCI work built a careful Jenkins setup: Jenkins inside Docker, 37 locked plugins, an admin account, and a demo job that passed. It proved the idea, and it also showed why Jenkins is a poor fit here:

  • It needs Docker (currently broken on this PC) and Java (not installed) before it can run anything.
  • Each run needed a person to make a snapshot, paste a 64-character code into a form, and click approve. That's hard for a beginner and awkward for an AI agent.
  • It doesn't read the existing .github/workflows files, so every check would be described twice.
  • It's a large system for one person to keep patched and safe.

Jenkins is a commercial kitchen. One developer working with AI agents needs a well-organised home kitchen. The EasyCI plan keeps the good ideas from the Jenkins work (exact-commit snapshots, checksums, releases that are never overwritten) and replaces Jenkins itself with a small tool.

6How this serves data science and your projects

NeedWhat EasyCI does about it
Long jobsTraining or full validation can take hours. Local runs have no per-minute bill, and the background supervisor keeps them alive.
GPUsGitHub's standard runners have no GPU, which is why JuliaFlow's hardware smoke test skips CUDA there. Your PC can run the real GPU path.
Big filesDatasets and models don't belong in Git. Run outputs go to a local store with checksums, alongside tools like DVC.
ReproducibilityEvery run records the commit, Julia and Node versions, package lock files and output checksums, so you can say later exactly what produced a model or release.
Comparing resultsA job can write a small metrics file (accuracy, run time, row counts) that shows up in the status, so a worse model is as visible as a failing test.

For JuliaFlow: you push a branch; EasyCI runs web, Julia and release checks on your PC; the pull request shows the three results; and easyci explain tells you in plain words which step failed and where its log is. When a release candidate passes, the exact package that was tested is copied into a numbered local release with a receipt. It's never rebuilt, so what you ship is exactly what was tested.
